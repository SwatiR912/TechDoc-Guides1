# Documentation process guides

How I run the parts of documentation work that are not writing: reviewing someone else's draft, planning a documentation project, and auditing a set that already exists.

These are working methods, written down so they can be handed to someone else. Each one is the version I would give a new team member on their first week, not a theory of documentation.

## The guides

| Guide | Use it when |
| --- | --- |
| [Running a documentation review](guides/running-a-documentation-review.md) | Someone has sent you a draft and you have to give feedback that improves it without demoralising them. |
| [Planning a documentation project](guides/planning-a-documentation-project.md) | A product is shipping and nobody has decided what documentation it needs. |
| [Auditing an existing documentation set](guides/auditing-an-existing-doc-set.md) | You have inherited documentation and do not yet know what is wrong with it. |

## Why these three

Writing is the visible part of the job and the smallest share of the hours. The work that decides whether documentation is any good happens before the writing, when scope is set, and after it, when someone reviews it honestly or audits what has drifted.

All three guides share one bias: **make the judgement explicit**. A review that says "looks good" teaches nobody. An audit that reports 300 findings without ranking them will be ignored. A plan that lists every document a product could have is not a plan.
