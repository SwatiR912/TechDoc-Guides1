# Documentation playbook

Methods for the parts of the documentation development lifecycle that are not writing: reviewing a draft, planning the documentation for a release, and assessing a set that already exists so it can be updated.

Each guide is written to be handed to someone else and followed — a working procedure rather than a theory of documentation.

## The guides

| Guide | Use it when |
| --- | --- |
| [Running a documentation review](guides/running-a-documentation-review.md) | A draft needs review feedback that improves it without demoralising the author. |
| [Planning a documentation project](guides/planning-a-documentation-project.md) | A product is shipping and nobody has decided what documentation it needs. |
| [Maintaining an existing documentation set](guides/maintaining-an-existing-doc-set.md) | Documentation has been inherited or has drifted over several releases, and needs assessing before it can be updated. |

## Why these three

Writing is the visible part of the job and the smallest share of the hours. What decides whether documentation is any good happens before the writing, when scope is set, and after it, when someone reviews it honestly or checks what has drifted since the last release.

All three guides share one bias: **make the judgement explicit**. A review that says "looks good" teaches nobody. A review that reports 300 findings without ranking them will be ignored. A plan that lists every document a product could have is not a plan.
